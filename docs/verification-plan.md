# 検証計画と受入れ基準

## 目的と範囲

CLI の実サイト調査品質と、目標を複数タスクに分解して人の好みを反映する Web 体験を別々に検証する。Web の体験モードは架空データを使用し、実サイト調査・VM発行の成功に数えない。

## 並行する実装と依存関係

| 作業 | 独立して進める範囲 | 統合時の依存 |
| --- | --- | --- |
| CLI品質 | 5サービスの実接続、検索導線、引用/候補対応、評価ケース | 既存 pi runtime |
| sandbox | NVIDIA公式仕様、VM向け実行計画、ポリシー、イメージ | CLIのJSONタスク契約、VM環境 |
| 参照UX | Grok Bot/OpenMausBot/rakazo の一次資料・画面・振る舞い | UI再現対応表 |
| ルーター/UX | DAG、同時実行上限、A2Aレビュー、承認、旅行/人生設計Mock | 上記の契約・検証結果を統合 |

CLIのサイト評価とWeb表示は独立。目標内では独立タスクを並列実行し、移動/予算レビューは候補の収集後、最終統合は承認後にだけ実行する。

## 自動検証

- 型チェックとビルド、既存テストを維持。
- 依存グラフが循環/不明依存/過大な並列数を拒否すること。
- 同時実行数が上限を超えないこと。依存先の失敗を成功扱いしないこと。
- ユーザー承認前に依存タスクが動かず、改訂前の承認を再利用できないこと。
- A2Aのレビュー指摘→修正→再レビューの上限と因果関係を保存すること。
- 再起動で承認待ち・履歴が復元されること。進行中の重複実行を防ぐこと。
- 入力検証、任意ファイル読み込み/コマンド実行の防止、loopback限定のWeb API。
- OpenShellのargv/ポリシー生成が公式コマンドに合い、キーを生成物に書かないこと。

## ブラウザ受入れ

デスクトップ/モバイルで、旅行と人生設計の各シナリオを開始→選択肢確認→好みの承認→並列調査→相互レビュー→途中のこだわり承認→最終プランまで操作する。別の選択で結果が変わる、自由入力が保存/反映される、やり直しで以前の承認が無効になる、更新後も選択を保持する、キーボードで操作できる、横はみ出し/JSエラーがないことを確認する。

## CLI実サイト評価

Hot Pepperグルメ/じゃらん/カーセンサー/SUUMO/Indeedを対象に、条件付きの日本語クエリで実行。トップ表示だけを成功としない。検索/候補詳細に進めたか、依頼条件を評価したか、候補ごとに実在引用を紐付けられたか、未知条件を未知と表示したかを記録する。掲載情報が取れない場合はサイトブロック・メンテナンス・モデル失敗を区別する。具体的な結果とtask IDは docs/cli-service-validation.md に保存する。

## 未提供環境

self-host VM の接続先や OpenShell gateway がない場合、実VMへの発行は未検証とする。生成計画/契約テストは実発行と区別する。本PRで予約・購入・応募・契約を行わない。


## trusted URL登録の受け入れ条件

- 一覧/未対応URL/本文不足/必須項目不足/文字化け/制限画面/認証転送を合格にしない。
- ホテル共通ナビや検索フォームだけで客室情報ありとしない。
- 同一対象の子ページ2件を2対象として登録しない。
- 有効期限切れ・失敗した再検証の旧URLは使用せず、未登録sourceでtrusted runを開始できない。
- 複数プロセスの更新で登録を失わず、古い結果が新しい結果を上書きしない。
- 公開ページ実測は最大2並列で取得。詳細取得評価と無料モデルによる回答品質評価を別ゲートにする。
- Linuxコンテナでcatalog/台帳の読み込みとCLI起動を確認し、実gateway検証は別に残す。

# 修正観点を次回の生成へ引き継ぐ

利用者が指摘した品質の問題を、今回だけのプロンプト修正で終わらせない。`config/review-perspectives.json`へ「問題・次回に問う質問・調査と修正の行動」を保存し、該当する新規生成と自己改善の実行前に毎回読む。現在は休憩場所の利用時間、未確認からの代替、移動・滞在の積み上げ、写真と地図の魅力などの観点を登録している。

## 生成前 → 検査 → 振り返り → 次回

1. 新しいタスクで適用する観点を選び、ID・質問・行動・版のハッシュを`task.reviewContext`へ保存する。元タスクのIDがなくても適用する。
2. モデルは質問へ答えるために公開情報を調べ、`read_task_state`で観点を読み直せる。休憩手順の利用時間が不足すると`verify_steps`は追加調査と代替の指示を返す。
3. 終了時にホストが休憩手順、全手順、行程stateの検査を再実行する。観点ごとの`checked`・`needs-attention`・`not-evaluated`を、回答ハッシュと観点の版に結び付けて保存する。
4. 次回の生成は直近の振り返りから観点別の指摘件数・検査済み件数を読み、再発している問題を確認できる。古い出典本文や個別の営業時間は再利用しない。

記録先は同じStoreの`review-perspectives/approved`（本人が追加した観点）と`review-perspectives/reflections`（ホストの検査結果）。リポジトリ既定の観点は別のStoreにも適用するが、個人が追加した観点・過去の振り返りは同じStoreの範囲で参照する。VMへホストの個人記録を自動転送する仕組みではない。

```sh
node dist/cli.js review-perspectives import my-review-perspective.json
```

入力例:

```json
{
  "id": "rest-weather-fallback",
  "domain": "trip",
  "origin": "user-correction",
  "concern": "雨の場合に屋外の休憩場所しか残らなかった",
  "question": "雨でも利用できる具体的な休憩先と移動を確認したか",
  "action": "屋内代替の場所・利用時間・費用を公式資料で調べ直し、移動と行程を再検査する"
}
```

本人が指定する観点はCLI・呼び出し側から登録する。実装中にホスト検証で発見して採用した観点は`host-verifier`として発見元タスクを記録し、本人の言葉と区別する。モデルに観点の承認・書込みツールは与えない。自動振り返りは新しい観点として自動昇格せず、既存の事実確認や安全境界を緩めない。これは手順の記憶でありモデルの重みを更新する学習ではない。

## 公園と休憩所の営業時間

以前の浜松案は公園ベンチを使う休憩に天守閣の営業時間を対応させようとして未確認になった。[観光局のMICE案内](https://mice-hamamatsu.jp/castlepark/)には公園は24時間開放と明記されている。この公園と天守閣、駐車場を別の対象として扱う。

- 通常施設は引用と`opens`・`closes`を照合する。
- 屋外公共空間に限り、同一の公園・広場について24時間・常時開放と明示する引用があれば、`access: "always-open"`で検査する。
- 駐車場・受付の時間や、別施設の引用は利用しない。通常時刻との併記も受け付けない。
- ベンチなど具体的な場所の引用は別の`fact`検査で確認する。古い設置記事は年月を示し、現在の空席の証明にしない。
- 公開案内で利用枠を確認しても、当日の空席・イベントによる規制・臨時閉鎖までは確約しない。

`checked`は宣言された数値・引用・状態契約の検査結果であり、自然言語の全主張を証明するものではない。写真や地図の魅力は人間の評価を自動で作らず、ホストの振り返りでは`not-evaluated`にする。

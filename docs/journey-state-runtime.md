# 距離と滞在を持つ行程state

09:00〜20:00の枠を確保するだけでなく、場所、施設内の階、移動区間、正味の滞在、待ち、休憩を関係付けて検査する。

`Place → TravelLeg → Place → Visit`という状態遷移を`actionPlan.journeyState`へ保存する。施設URLを対象識別子として正規化し、同じ施設の階別体験は一回の訪問に集約する。別の施設へ出かけて戻った場合は別訪問に分ける。移動なしの場所変更、前区間とつながらない出発地点、二重計上、食事や待ちを体験時間へ混ぜる案を検出する。

## 距離と時間

徒歩の各端点には引用付きの緯度・経度が必要。両地点名・徒歩・分数を持つ公開資料や、同じ方向・手段・ペースの履歴でも照合できる。直線距離からの推定では、仮の迂回係数1.3、ゆっくり50m/分・通常65m/分を初期値にする。これらは計画の仮定で、実測距離や統計的に学習した歩速ではない。

移動本体、待ち、乗換・乗降、余裕を別々に持ち、合計が手順の所要時間と一致するか検査する。余裕は最低3分。館内移動にも初期値5分、大きな階差には10分を確保する。屋外広場や別施設への移動を「館内」とすることで、距離不足を回避できない。

参考として調べた[OSRMの公式API仕様](https://project-osrm.org/docs/v5.24.0/api/)でも、経路の距離・所要時間と直線距離からのfallbackを区別し、移動モードはサーバー側のプロファイルで決まる。今回の実装は公共デモサーバーへ自動接続せず、初期推定と本人の申告実績・提供元の経路見積を分離する。道路経路を確認したという表示にはしない。

## 滞在と休憩

初期の最低滞在は博物館60分、体験30分、展望25分、公園20分、カフェ30分、食事40分、休憩10分。参考の滞在幅も併記する。施設の種類をモデルが宣言した上で固定ルールを適用する仕組みであり、内容の魅力や全ての施設の適切な滞在時間を証明する値ではない。

同一施設内の見学を休憩や階移動で分割した場合は、見学だけを合算して検査する。休憩と移動は正味滞在へ加算しない。ゆっくりの計画では120分、通常では180分を超えて休める枠なしに続けない。15分以上の休憩・食事・カフェを回復枠とし、行列・入店待機は回復へ数えない。長い滞在には具体的な過ごし方を再確認する注意を返す。

明示時刻があっても8時間以上の行程は状態・手順検査の対象とする。09:00〜20:00のように朝から夜の枠では、午前の体験、昼食、午後、夕食、帰路も必要になる。短い明示枠の既存回答と、過去の保存回答には新しい状態を後付けしない。

## 過去の状態

| 区分             | 保存と参照                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 過去の生成案     | 計画として保存。場所・区間の推定距離・予定滞在・所要時間を参照できるが、実際に歩いた／滞在した実績へ昇格しない            |
| 本人の申告実績   | 呼び出し側・CLIで取り込む。同じ施設、移動方向、手段、ペースだけを参照。本人申告でありセンサーで検証済みという意味ではない |
| 提供元の経路見積 | 観測した移動と区別。7日以内の同条件だけを参照                                                                             |
| 履歴なし         | 未登録・対象外を明示し、初期仮定で見積もる。実績件数や「学習済み」を創作しない                                            |

本人の実績は2年以内を参照対象とする。滞在は中央値側、移動は上位側の記録を参考に、初期の最低枠を下回らないよう比較する。少数記録は統計的な確信と呼ばない。天候や人数など、記録にない条件まで照合したとは扱わない。

履歴領域が空なら同じStoreの過去タスクから最大20件を計画として取り込み、関連する新しい計画を最大5件参照する。実際に移動した記録へは変換しない。

記録は同じStoreの`journey-memory/observations`と`journey-memory/plans`へ別保存する。モデルのツールには観測記録を追加する機能を与えず、生成終了時には計画だけを保存する。サンドボックスの成果物はゲストの履歴や判定を信用せず、ホストで計画と検査を再構成する。VMへ個人履歴を自動転送する実装ではない。

```sh
node dist/cli.js journey-history import my-observed-trips.json
node dist/cli.js journey-history show
node dist/cli.js journey-history places <task-id>
```

入力は1〜100件の配列。`id`、`kind`（travel/dwell）、`basis`（user-observed/provider-estimate）、`minutes`、`pacing`、`occurredAt`、`sourceNote`が必要。移動には`fromKey/toKey/mode`、滞在には`placeKey/category`を持たせる。`meters`は取得できた場合だけ指定する。`places`コマンドで返る`venueKey`を滞在、`endpointKey`を移動に使う。移動のキーには階を含め、同じ施設の2階→45階と逆方向を区別する。施設URLのない代表点は名称と座標を組み合わせ、同名の別地点を混ぜない。生成案・未来の記録・不正な値・既存IDの上書きは受け付けない。

## 生成と改善への接続

`stage_plan`・`verify_steps`・`read_journey_state`・`finish_task`で現在の計画を再検査する。足りない座標や経路情報を調べ、指摘を直して再提出する。`assessSpecificity`にも不足を組み込むため、既存の自己改善診断は距離不足・短すぎる滞在・移動の不連続を完了扱いにしない。

HTMLには徒歩距離の見積、歩行時間、未算出区間、体験／食事／休憩／移動／待ちの配分と、その根拠を表示する。出典の完全性・数値・状態遷移を検査する契約であり、道路の通行可否、当日の混雑・空席、施設の意味解釈全体を証明するものではない。

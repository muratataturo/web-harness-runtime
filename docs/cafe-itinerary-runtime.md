# カフェも、一日の目的にする

[資料照合して仕上げた上野のカフェ旅行を開く](cafe-day.html#itinerary)。公式のハーブティーの写真と、動物園からひと息へつなぐ行程を表示する。HTMLと隣の`answer-assets/`を一緒に保存して開ける。

## 候補を取得する

「カフェ」「喫茶」「珈琲」「コーヒー」「cafe / café / coffee」を取得意図として認識する。適合する飲食ソースが未指定なら、Hot Pepperグルメを調査元へ追加する。`RUNTIME_PROFILE=rakuten`では楽天ぐるなびを使用する。明示された「カフェ不要」「含めない」などを優先する。近隣の全店舗を網羅するPlaces API検索ではない。入力地域と好みを短い検索語にして、実在する店舗詳細へ進む。

店舗公式の取得例として`shop.create-restaurants.co.jp`を版管理されたアダプターへ追加した。店舗番号ごとに個別対象を識別し、住所・営業時間・メニューの本文を検証する。系列の別店舗の情報で補完しない。個別商品価格が未掲載でも捏造を要求せず、予算枠として見積を明示できる。

ソース選択、ローカル調査、sandboxの接続先規則で同じルーティングを使う。外部ページのリンクだけで新しい公式ドメインを自動許可しない。未対応の店は入力URLとして指定できるが、全ての公式サイトの取得成功を保証するものではない。

## 行程と費用に組み込む

新しい並行スケジュールは作らず、既存の`actionPlan`と`journey-map`へ組み込む。

- `where / action / how`で店名、選ぶ理由、注文・味わい方を具体化する。
- 営業時間と所在地の引用を同一店舗から取得し、滞在手順の`evidenceIds`へ結び付ける。既知サービスの店舗一覧を個別店の根拠にしない。
- 前後の移動、入店待機、飲食の滞在を別手順にする。時間の重なりや予算合算は共通の契約で検査する。
- 飲食の費用を実際に注文する手順の`costItemIds`と主案`budget`へ紐付ける。待機手順には飲食費を重ねて要求しない。
- 平均予算をドリンクの掲載単価へ転用しない。価格未取得なら`estimate`。空席や当日の提供可否は未確認として残す。
- `branches`に満席・休業時の判断条件と具体的な次の行動を表示する。

カフェ依頼のある旅程で不足があれば、共通の具体性品質ゲートが修正を求める。これは文字列と引用の対応を検査する実行契約で、自由文の意味・徒歩経路・営業時間内の到着を完全に証明するものではない。店名・アクセス・営業情報の内容は出典を併記して確認できる。

## 写真と自己改善

カフェは「休憩」に分類されても主要な写真付き体験として扱う。`inspect_photo`で保存ページの実画像をモデルに見せ、YOUR DAY、全手順、地図へ結び付ける。写真だけで当日の献立や空席を保証しない。移動や入店待機はカフェ体験の写真必須判定から除く。

オンライン改善は不足した公開情報を再調査できる。offline視覚改善は保存済みの行程と写真候補を使い、元の店舗・料金・時間を変えない。そもそもカフェが未調査なら、offlineだけで架空の店を足して合格にはしない。既存の10秒レビューで受けた実回答は次の生成への改善指針に使える。人間の魅力度は未評価。

実生成では、引数形式を間違えたモデルが正しい形式を推測し続ける問題も見つかった。Codexの修正応答へ、誤ったフィールドに対応する許容値と必要項目を追加した。入力値や外部ページの指示を修正契約には混ぜない。

[生成・改善の記録](evidence/cafe-itinerary-generation.json)、[ブラウザ検証](evidence/cafe-itinerary-qa.json)。凍結した実出力のHTML再生と、実モデルの生成は区別して記録する。写真の権利は掲載元に帰属する。

## 前回までの状態

最終の保存回答は8手順、写真2枚、2人の現地予算8,900円。カフェ滞在は13:20から80分、入店待ちは20分を上限にする提案。限定甘味の掲載価格と飲物・軽食の見積を分けた。移動時間・当日提供・共有可否・空席は未確認。掲載写真から当日提供を確定しない注記もホスト側で表示する。

カフェの引用・費用の対応検査と視覚品質ゲートは通過した。ただし、モデルは施設の候補比較配列を最後に省略し、元Taskの状態は`blocked`のままである。また、最新の具体性再検査では動物園内の休憩場所1箇所が抽象的として残った。成功済みの完全な調査とは数えず、画面では「未確認を含む暫定案」として提示する。新しいruntimeでは、候補比較が空でも行程がある場合に具体性・カフェの検査を行い、この不足を隠さない。


## 正式版の仕上げ

現在の回答は10手順・写真2枚、主案は2人7,060円。一般入園600円×2、定番キャラメルナッツパンケーキ2枚1,900×2、単品フレッシュハーブティー（ホット）1,030×2を公式掲載額から計算した。セット条件や共有可否に依存しない。休日メニューPDFの3枚2,100／2枚1,900の対応は紙面も表示して照合した。価格・税区分の表示内容を越えた支払額の確約はしない。

休憩は12:00から20分、東園・サル山前のさるやまキッチン無料休憩所。名称・所在地・屋内の無料休憩所併設・営業時間10:00〜16:30を引用した。候補比較は動物園、主案カフェ、満席時のスターバックス上野恩賜公園店の3件。代替店のTall限定・特定立地Bは、その店の公式情報として明示し、主案の価格を転用しない。代替店は店頭確認後に2人3,000円以内で注文する条件付きの切替先で、主案の費用合計には含めない。

「正式」は営業予定・掲載額・所在地・利用方法を確認した実行プランという意味。予約・未来の空席の確約ではない。公式で予約受付なしを確認し、席は到着時に判断、待ち時間は20分で区切る運用にした。臨時変更・在庫・当日の席は現地の案内を優先する。これらを調査未完と混同せず、5つの確認項目と当日の切替手順で表示する。

今回、元の自動モデルは資料取得後の仕上げを完了できなかった。公開資料を照合してCodexが最終編集し、全て同じ具体性・視覚・カフェ品質ゲートで再検証した。候補の適用条件、掲載額合算、写真出典を再確認し、共通改善ループの診断もcompleteになった。これを無人モデル生成の成功率や重み学習の成果として数えない。画面とスナップショットに資料照合・編集済みという区別を残す。人間による魅力度は未評価。

## runtimeに追加した仕組み

- 公開PDFは同じ許可ホスト・DNS・転送・HTTP拒否規則で取得。16MiB・20ページ・ダウンロード180秒・別worker解析8秒を上限にする。PDF内のスクリプトは実行せず、外部リソース取得を無効化。日本語の文字マップと標準フォントはローカルのPDF.jsリソースのみ使用する。画像だけの文書や解析不足を文字として補わない。引用にページ番号を残す。
- `criteria.appliesTo`で対象の個別URLを指定できる。対象外をunknownのまま適用対象の確認率から除く一方、必須条件の対象候補そのものを消すことは認めない。改善契約・sandbox回収にも同じ条件を通す。
- `stage_plan`→`stage_visual`→`finish_task`で草案を分けて保存できる。比較の修正時に保存済みの行程・写真を省略しても保持するが、最終提出時にすべての引用を再検査する。行程を再stageすると以前の視覚草案を取り消す。
- 正式版には`actionPlan.verification`を要求する。対象日とopening/prices/seating/comparison/restの5種、引用、実際の手順参照が必要。主案の未確認単価は残さず、seatingだけarrival-checkとして未来の席確約・予約完了を拒否する。
- モデルが「ユーザーの指示で候補なし」と創作して未完了を保存することを拒否し、実際の不足として記録させる。

Node.jsは22.13以降。PDF読み取りはunpdf 1.6.2とPDF.js 6.5.438に固定した。設計参照: [unpdf公式](https://github.com/unjs/unpdf)、[PDF.js公式](https://github.com/mozilla/pdf.js)。ダウンロードと解析の制限はホスト側で管理し、引用確認は自由文の意味全体や将来の営業を完全に証明するものではない。

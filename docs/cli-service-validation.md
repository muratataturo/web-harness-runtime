## 観測から実装した改善

1. **一覧ページの候補化を拒否**: サービスごとの個別エンティティIDを判定。検索一覧・特集を1店舗・1台・1部屋として推薦できなくした。
2. **同一エンティティの関連ページを扱う**: Beautyに加え、同一店舗のランチ・メニュー、同一宿の温泉ページ等の根拠を対応付け。別店舗・別車両の根拠流用は拒否。同じIDの追跡パラメータ違いによる重複候補も拒否。
3. **引用修復を支援**: 不一致の引用を自動承認せず、同じ取得本文から近い抜粋をエラーに添えて返す。短い連続引用を使い、離れた箇所を連結しないよう指示。
4. **タイトルも根拠に含める**: 取得本文にページタイトルを先頭追加。タイトルに依存する説明を別の無関係な引用で裏付ける問題を減らす。
5. **候補リンクの発見品質**: リンクをURLで重複除去し、個別詳細を優先。SUUMOでは部屋単位の `bc_` を建物単位の `jnc_` より優先。
6. **サイト状態を分離**: `assessPage` で通常取得／情報更新遅延／メンテナンス／アクセス制限／404／本文不足を区別。メンテナンス・制限ページは候補として承認できない。
7. **読み込みエラーの扱い**: ナビゲーション応答が失敗しても、正確に同じURLで有効な本文が描画済みなら一度だけ読み取る。別ページを取得成功と偽装しない。CLIの非ゼロ終了時にもJSONの構造化エラーを取り出す。
8. **数値条件の説明**: 総額、管理費合算、給与下限、対象駅への徒歩、施設風呂と客室風呂の区別をサイト別に指示。
9. **再実行可能な評価**: `src/service-evals.ts` が `loadServiceCases`、`runServiceEvaluations`、`probeServiceCases`、`evaluateServiceTask` を公開。API課金なしのブラウザ検証とLLM比較回答の合否を区別して保存。
10. **無料APIの枠を識別**: 日次枯渇429・短期の429・認証不良・エンドポイント不在を `providerFailureKind` で区別できるようにした。

## PR の検証計画

依存関係と並列度:

```text
定義・出典確認
  ├─ ブラウザ可用性チェック（並列最大2、API消費なし）
  │    └─ 一覧→個別詳細の遷移確認
  ├─ 引用・個別ID・制限画面のユニットテスト（外部APIなし）
  └─ LLM回答評価（無料枠確認後、原則並列1）
       └─ 条件網羅・引用と主張の意味一致を人が確認
            └─ 多分野ゴールの統合・相互レビューへ
```

- 必須の自動チェック: TypeScript、全テスト、build、差分チェック。
- LLM評価の合格には、指定2件、個別詳細URL、全条件の評価、必須条件の充足、引用の実在と同一対象への対応が必要。
- `validated` は構造チェックを満たしたという意味で、引用が主張を意味的に裏付けるかは人のレビューが必要。
- 429やメンテナンスは正しく失敗できたとしても、推薦品質の合格として数えない。
- 無料枠回復後はグルメを最初に1ケースだけ再実行し、引用の修復回数と完走時間が改善することを確認してから他ケースを順次実行する。
- じゃらんとSUUMOの詳細取得はブラウザの負荷・応答・ページ導線を先に解決し、取得できないまま推測した候補で回答しない。

## 追加切り分け: ナビゲーション待機（2026-11-10 06:10〜06:15 JST）

追加調査でも無料モデルは呼び出していません。結論として、**待機フラグの変更だけでじゃらん／SUUMOの個別詳細取得が成功したとは確認できませんでした**。`src/browser.ts` に未実証のフラグや回避処理は追加していません。

確認した公式仕様:

- インストール済み0.41.2の `open --help` に `--wait-until` はありません。[公式CLIパーサー](https://github.com/vercel-labs/agent-browser/blob/main/cli/src/commands.rs)でも、openから`waitUntil`を渡す経路は公開CLI引数として実装されていません。
- [公式native実装](https://github.com/vercel-labs/agent-browser/blob/main/cli/src/native/actions.rs)のnavigate既定は`Load`です。
- `agent-browser mcp call agent_browser_open` に `waitUntil: domcontentloaded` を渡すと、0.41.2はUnknown argumentとして拒否しました。
- `--wait-until domcontentloaded` を正式に受け付けるのは `diff url`。これを通常のopen代用として本体に組み込まず、診断に限って使用しました。

追加実験:

| 実験 | 対象 | 結果 |
| --- | --- | --- |
| ブラウザ起動後、固定コードでlocation.assignし、URL・document.readyState・本文長の実条件を待つ | じゃらん箱根地域一覧、SUUMO部屋詳細 | どちらもdaemon応答なしの`outcome_unknown`。固定sleepで成功扱いにしていない |
| 従来openで実在確認済みの個別詳細を直接開く | [箱根 強羅 月の泉](https://www.jalan.net/yad375320/)、[SUUMO部屋詳細](https://suumo.jp/chintai/bc_100521216176/) | どちらも`outcome_unknown`。同一設定のget urlはabout:blankを返し、採用可能な本文を取得できなかった |
| 正式なDOMContentLoaded待機で同一URL同士を比較する診断 | じゃらんの同じ宿詳細 | `diff url ... --wait-until domcontentloaded`でも`outcome_unknown` |

したがって、単純なloadイベント待機だけを原因と断定せず、agent-browser daemon・CDP・対象サイトの読み込みの切り分けを残します。今回の専用セッションは明示的に終了しています。実測ファイルは `.runtime/fast-navigation-probes/` と `.runtime/direct-detail-probes/` に保存しました。

公開用の構造化ログでは、ローカルworkspaceの絶対パスを `<workspace>` に正規化しています。URL・状態・判定の内容は変更していません。

## 公開HTML経路での解決（2026-11-10 06:55 JST）

ブラウザ経路が応答しない同じ詳細URLでも、通常の公開HTTPS GETは200で本文を返していた。そこでじゃらん・SUUMOをサーバーHTML優先にし、ブラウザとは別の取得方式として記録する実装を追加した。ブラウザ制御内部の原因を解明した、またはChromeで詳細を描画できたという意味ではない。

- じゃらん: HTTPの `charset=Windows-31J` を `shift_jis` としてデコード。箱根一覧から天成園・ホテル南風荘の詳細を取得し、温泉・露天風呂・アクセスの本文が読めることを確認。
- SUUMO: UTF-8で検索本体の物件詳細2件を取得。家賃・管理費・1LDK・武蔵小杉の記載を確認。検索結果本体のjncリンクを、別の駅を含む周辺物件広告のbcリンクより優先する。
- どちらも一覧＋詳細2件すべてHTTP200。取得結果は `acquisition.kind=public-html`、status、charset付き。同じ引用検証とエンティティ対応を利用する。
- 許可ホスト・公開IP・各転送先を検査し、認証情報やcookiesを送らず、HTML内のJavaScriptを実行しない。HTTP拒否を再試行で回避しない。
- `inspect_page` のブラウザsnapshotをHTML取得ページに偽装しない。動的な空室・掲載継続の確認として扱わない。
